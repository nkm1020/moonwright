## How to read

Every injection fails one robot mid-task; the agent locks the tasks underway, drops the robot and asks CP-SAT to reschedule the remaining work first. `solver-only` is the share of replans CP-SAT verified on its own (Nemotron not asked); `escalated` the share whose remaining work was provably infeasible, so the solver's conflict core went to Nemotron; `esc. verified` how many escalations came back with a repair the solver verified; `recovered` the share of replans that ended with a verified schedule either way; `within horizon` the share whose mission then finished by the deadline in the simulator. Every one of these rates is over the `askable` injections: `replanned` minus `not asked`, which is `not_asked_sole_type` (the failed robot was the only one of its type and still owned work, so the remaining graph can only fail on `capability` and, under `--sole-of-type solver`, Nemotron is deliberately not asked: nobody can recover that work without re-typing it) plus `not_asked_budget` (the `--max-escalations` budget was spent before this injection, so its outcome is unknown); the `not asked (sole / budget)` column counts them, so `solver-only + escalated + solver_failed = askable` and `askable + not asked = replanned`. Intervals are Wilson 95 %. `median solve` is CP-SAT's time for the verified schedule, `median LLM` the model calls' latency of an escalation; cost is at the Token Factory list prices. An escalation without an answer (`escalated_no_answer`) is an offline run without a recorded repair, not a model failure. `escalation cores` counts the conflict families behind the escalations: `capability` means the failed robot was the only one of its type (a repair can only re-type that work), `energy` / `horizon` that the surviving fleet lacks battery or hours for the work as scoped. With `--all-tasks` a robot with many tasks weighs more (one injection per task and fraction) and a late-task injection is easy; the first-task default weighs every robot with work the same.
